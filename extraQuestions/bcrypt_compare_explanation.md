## 🚀 How bcrypt.compare() works

A valid doubt often arises: if we input a raw password, how does it compare to the hashed version stored in the database if it isn't hashed with the same salt? **`bcrypt.compare()` DOES NOT compare the raw string directly to the hash, nor does it decrypt the hash.**

### 📌 Here is what actually happens:

**During Signup:**
```javascript
password: "hello123"
salt: "random_xyz" (generated by bcrypt.genSalt())

bcrypt.hash("hello123", "random_xyz") 
  → "$2b$10$random_xyz...HASHED_RESULT_abc"
       ↑      ↑                ↑
    version  salt           actual hash
    
// This entire string is saved in MongoDB
```

**During Login (`bcrypt.compare`):**
```javascript
User types: "hello123"  (raw password)
Stored in DB: "$2b$10$random_xyz...HASHED_RESULT_abc"
```

**What `bcrypt.compare("hello123", "$2b$10$random_xyz...HASHED_RESULT_abc")` does internally:**

```
Step 1: EXTRACT THE SALT from the stored hash
        "$2b$10$random_xyz...HASHED_RESULT_abc"
                 ↑
         Extracted: "random_xyz"

Step 2: Hash the raw password using THAT SAME EXTRACTED SALT
        bcrypt.hash("hello123", "random_xyz") 
        → new hash generated: "HASHED_RESULT_abc"

Step 3: Compare them:
        New hash:  "HASHED_RESULT_abc"  
        Stored hash: "HASHED_RESULT_abc"  
        MATCH ✅ → returns true
```

### 📌 Example — If a wrong password is given:

```javascript
User types: "wrong999"
Stored in DB: "$2b$10$random_xyz...HASHED_RESULT_abc"

Step 1: Extract salt: "random_xyz"
Step 2: bcrypt.hash("wrong999", "random_xyz") → "SOME_OTHER_HASH_def"
Step 3: "SOME_OTHER_HASH_def" !== "HASHED_RESULT_abc"
        NO MATCH ❌ → returns false
```

### 📌 In one sentence:

> **`bcrypt.compare()` doesn't decrypt the password. It hashes the incoming raw password again (using the exact same salt that is embedded inside the stored hash string), and then compares the two hashes.**

The salt is not stored as a separate field in the database — it remains embedded within the hash string itself (the characters after `$2b$10$`). This is why there's no need to manually store the salt at the time of signup.

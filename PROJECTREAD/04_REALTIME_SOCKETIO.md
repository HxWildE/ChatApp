# 🌟 04 — Real-Time: Socket.io Deep Dive
### 📌 WebSockets, Events, Online Presence, and Typing Indicators

> **Reading Goal**: Understand how HTTP differs from WebSocket, how Socket.io works end-to-end in this app, and be able to trace every real-time event from sender to receiver.

---

## 🚀 1. HTTP vs WebSocket — The Core Difference

### 📌 HTTP (Request-Response)

```
Client                     Server
  |                           |
  |──── GET /messages ───────>|
  |                           |
  |<─── Response: [msg1, msg2]|
  |                           |
  |  (connection closed)      |
  |                           |
  |  [To get new messages,    |
  |   client must ask again]  |
```

HTTP is stateless and pull-based. Client always initiates. Server can't push data to client.

### 📌 WebSocket (Persistent Bidirectional)

```
Client                     Server
  |                           |
  |── HTTP Upgrade Request ──>|   ← Starts as HTTP
  |<── 101 Switching Protocol-|   ← Server agrees
  |                           |
  |  [Connection stays OPEN]  |
  |                           |
  |<── "newMessage" event ────|   ← Server can push anytime
  |                           |
  |──── "typing" event ──────>|   ← Client can push anytime
  |                           |
  |  [Until disconnect]       |
```

WebSocket is stateful and push-based. One long-lived connection. Both sides can send at any time.

**Why does chat need WebSocket?** — With HTTP, to receive a new message you'd have to poll every few seconds ("polling"). WebSocket lets the server push the message the instant it arrives. Zero delay, no unnecessary requests.

## 🚀 2. Socket.io vs Raw WebSocket

Socket.io **wraps** WebSockets and adds:
- 💡 **Auto-reconnection** — network hiccup? It reconnects silently
- 💡 **Event-based API** — `socket.emit("typing", data)` vs raw WebSocket binary framing
- 💡 **Rooms** — group sockets together (not used here but available)
- 💡 **Fallback** — if WebSocket isn't supported, it uses long-polling automatically
- 💡 **Server-side broadcasting** — `io.emit()`, `io.to(id).emit()`, `socket.broadcast.emit()`

## 🚀 3. Server-Side Socket.io Setup

### 📌 Attaching to the HTTP Server

```js
// server.js
import http from 'http';
import { Server } from "socket.io";

const app = express();
const server = http.createServer(app);  // Shared server
export const io = new Server(server, {  // Socket.io attached to same server
  cors: { origin: "*", methods: ["GET", "POST"] }
});
```

Both Express (HTTP) and Socket.io (WebSocket) share the same port (5000). The server knows which protocol to use based on the request type.

### 📌 The Connection Map

```js
export const userSocketMap = {};  // { "mongoUserId": "socket_abc123" }
```

This maps user identities (stable MongoDB IDs) to their current socket IDs (temporary, changes each reconnection).

**Why not use socket IDs directly?** — Socket IDs are generated by Socket.io and change on every reconnect. MongoDB user IDs are permanent. We need a stable identifier to route messages to the right person.

### 📌 The Connection Handler

```js
io.on("connection", (socket) => {
  // Runs every time a new WebSocket connection is established
  const userId = socket.handshake.query.userId;
```

`socket.handshake` — When a WebSocket connection is established, there's an initial HTTP handshake. Query params attached to the connection URL are available here.

**Client sends (in AuthContext.jsx):**
```js
const newSocket = io(backendUrl, {
  query: { userId: userData._id }
});
```

**Server receives:**
```js
const userId = socket.handshake.query.userId;  // "67fb37abc..."
```

```js
  if (userId) userSocketMap[userId] = socket.id;
  // Store: { "67fb37abc...": "socket_xyz..." }
  
  io.emit("getOnlineUsers", Object.keys(userSocketMap));
  // Broadcast to ALL connected clients: here's who is online
```

## 🚀 4. Complete Real-Time Message Flow

### 📌 Sending a Message (Full End-to-End Trace)

```
[User A types "Hello" and presses send]
            │
            ▼
ChatContainer.jsx — handleSendMessage()
  → setInput("") — clears the input box immediately (optimistic UX)
  → calls sendMessage({ text: "Hello" }) from ChatContext
            │
            ▼
chatContent.jsx — sendMessage()
  → axios.post("/api/messages/send/[UserB_id]", { text: "Hello" })
  → Header: token: <User A's JWT>
            │
            ▼ [HTTP POST over internet/localhost]
            │
server.js → Express → messageRoutes → protectRoute middleware
  → Verifies JWT → attaches User A to req.user
            │
            ▼
messageController.js — sendMessage()
  → senderId = req.user._id (User A's ID from JWT)
  → receiverId = req.params.id (User B's ID from URL)
  → Message.create({ senderId, receiverId, text: "Hello" })
  → Saved to MongoDB ✓
            │
            ├──[Socket Path]───────────────────────────────────────┐
            │                                                       │
            │  receiverSocketId = userSocketMap[receiverId]         │
            │  → "socket_UserB_abc123"                              │
            │                                                       │
            │  io.to("socket_UserB_abc123").emit("newMessage", msg) │
            │                                                       ▼
            │                                    [WebSocket push to User B's browser]
            │                                                       │
            │                                    chatContent.jsx — socket.on("newMessage")
            │                                      → Is selectedUser === User A? YES
            │                                      → setMessages([...prev, newMessage])
            │                                      → ChatContainer re-renders
            │                                      → "Hello" appears instantly ✓
            │
            ▼ [HTTP Response back]
chatContent.jsx — receives { success: true, newMessage }
  → setMessages([...prev, newMessage])
  → User A also sees their own message appear ✓
```

**Key insight**: The message appears for User A via HTTP response, and for User B via WebSocket push. Both paths update the same `messages` state.

## 🚀 5. Online Presence System

### 📌 How It Works

```
User A opens app → AuthContext.connectSocket() called
    → io("http://server:5000", { query: { userId: "A_id" } })
    → WebSocket handshake
    
Server → io.on("connection") fires
    → userSocketMap["A_id"] = "socket_abc"
    → io.emit("getOnlineUsers", ["A_id"])  ← broadcast to EVERYONE
    
All connected clients:
    → socket.on("getOnlineUsers", (userIds) => setOnlineUsers(userIds))
    → Re-renders with ["A_id"] in onlineUsers array

User B opens app → same process → userSocketMap["A_id", "B_id"]
    → io.emit("getOnlineUsers", ["A_id", "B_id"])
    → Everyone updates
    
User A closes browser → socket.on("disconnect") fires
    → delete userSocketMap["A_id"]
    → io.emit("getOnlineUsers", ["B_id"])
    → Everyone removes A from their online list
```

### 📌 Frontend Display

```jsx
// Sidebar.jsx
onlineUsers.includes(String(user._id))
  ? <span className='text-green-400 text-xs'>Online</span>
  : <span className='text-neutral-400 text-xs'>Offline</span>
```

`onlineUsers` is an array of IDs. `.includes()` checks if the current user's ID is in it.

**Why `String(user._id)`?** — MongoDB ObjectIds can be objects when coming from Mongoose. The `userSocketMap` keys are strings (from the socket query). `String()` ensures consistent comparison.

## 🚀 6. Typing Indicators — Complete Flow

### 📌 Sender Side (ChatContainer.jsx)

```
User A starts typing in the input field
    │
    ▼
handleInputChange(e) called on every keystroke
    │
    ├─ setInput(value) — update the input display
    │
    ├─ socket.emit("typing", { receiverId: "B_id" })
    │    → Server receives → routes to User B's socket
    │
    └─ typingTimeoutRef = setTimeout(() => {
           socket.emit("stopTyping", { receiverId: "B_id" })
       }, 1500)
       → Reset this timer on every new keystroke
       → Only fires if 1.5s of inactivity passes
```

**The debounce pattern visualized:**
```
Keystroke: H  e  l  l  o  [1.5s pause]
           │  │  │  │  │       │
           ▼  ▼  ▼  ▼  ▼       ▼
emit: T    T  T  T  T  T      STOP
(each T = "typing", each T resets 1500ms timer)
```

### 📌 Server Side (server.js)

```js
socket.on("typing", ({ receiverId }) => {
  const receiverSocketId = userSocketMap[receiverId];
  if (receiverSocketId) {
    io.to(receiverSocketId).emit("typing", { senderId: userId });
  }
});
```

Server is just a relay here. It doesn't store typing state — just forwards the event to the target socket.

### 📌 Receiver Side (ChatContainer.jsx)

```jsx
useEffect(() => {
  if (!socket || !selectedUser) return;
  
  const handleUserTyping = ({ senderId }) => {
    if (String(senderId) === String(selectedUser._id)) {
      setIsTyping(true);  // Show "typing..." indicator
    }
  };
  
  const handleUserStopTyping = ({ senderId }) => {
    if (String(senderId) === String(selectedUser._id)) {
      setIsTyping(false);  // Hide "typing..." indicator
    }
  };
  
  socket.on("typing", handleUserTyping);
  socket.on("stopTyping", handleUserStopTyping);
  
  return () => {
    socket.off("typing", handleUserTyping);    // Cleanup
    socket.off("stopTyping", handleUserStopTyping);
  };
}, [socket, selectedUser]);
```

**Why the guard `String(senderId) === String(selectedUser._id)`?**

Without it, if User C is typing to User B, and User B has User C selected, that's correct — show typing. But if User B has User A selected, typing events from User C should be ignored. The check ensures the typing indicator only shows for the person you're currently chatting with.

**The cleanup function (return `() => {...}`):**

When `selectedUser` changes (you switch chats), React runs the cleanup first, removing old event listeners. Then the effect runs again with new listeners for the new selectedUser. Without cleanup, old listeners accumulate — you'd see typing indicators from the wrong people.

## 🚀 7. Socket.io Client Setup — `connectSocket` in AuthContext

```jsx
const connectSocket = (userData) => {
  if (!userData || socket?.connected) return;  // Don't double-connect
  
  const newSocket = io(backendUrl, {
    query: { userId: userData._id }  // Send userId in the connection handshake
  });
  
  newSocket.connect();
  setSocket(newSocket);
  
  newSocket.on("getOnlineUsers", (userIds) => {
    setOnlineUsers(userIds);
  })
}
```

**`socket?.connected`** — Optional chaining: if socket exists and is connected, don't make another connection. Prevents duplicate sockets on re-renders.

**When is `connectSocket` called?**
1. On login/signup: after credentials verified, before navigating
2. On page load: after `checkAuth` confirms the token is valid

**On logout:**
```jsx
socket?.disconnect();
```
Closes the WebSocket. The server's `disconnect` event fires, removing the user from `userSocketMap`.

## 🚀 8. Events Reference Table

| Event Name | Direction | Emitted By | Received By | Data |
|-----------|-----------|-----------|------------|------|
| `connection` | Client→Server | Socket.io auto | Server | socket object |
| `disconnect` | Client→Server | Socket.io auto | Server | — |
| `getOnlineUsers` | Server→Client | Server | All clients | `[userId1, userId2, ...]` |
| `typing` | Client→Server→Client | ChatContainer | Server → target client | `{ receiverId }` / `{ senderId }` |
| `stopTyping` | Client→Server→Client | ChatContainer | Server → target client | `{ receiverId }` / `{ senderId }` |
| `newMessage` | Server→Client | messageController | Target client (receiver) | `{ message object }` |

## 🚀 9. What Happens If Socket.io Is Removed?

| Feature | With Socket.io | Without |
|---------|---------------|---------|
| Receive new messages | Instant (push) | Must refresh page |
| Typing indicators | Real-time | Not possible |
| Online presence | Instant updates | Not possible |
| Message delivery | Save + push | Save only |

The app would still work as a "refresh to see messages" app — all HTTP endpoints remain functional. But it wouldn't be a real-time chat anymore.

## 🚀 10. Production Considerations (What You'd Change)

These are common interview follow-up questions:

**Q: userSocketMap is in memory — what happens with multiple servers?**
User A connects to Server 1, User B to Server 2. Message from A routes to `userSocketMap` on Server 1, User B's socket isn't there. Message not delivered.

**Fix**: Use **Redis Pub/Sub** as a shared message bus. Socket.io Redis adapter (`@socket.io/redis-adapter`) handles this.

**Q: Token in socket handshake — how would you secure it?**
Current: userId in query string (visible in logs).
Better: Send JWT in the socket auth handshake:
```js
const socket = io(url, { auth: { token: localStorage.getItem("token") } });
// Server: socket.handshake.auth.token
```

**Q: The typing debounce — what's the right delay?**
1.5 seconds is a reasonable UX choice. Too short → spammy events. Too long → laggy UX.
